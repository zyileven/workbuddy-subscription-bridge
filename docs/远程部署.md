# 另一台电脑部署与持续运行

项目只需要 Git、Docker 和 Docker Compose。另一台电脑需要能够访问 GitHub、
OpenAI 登录和推理接口。本文示例仓库为私有仓库，克隆时使用自己的 GitHub
登录凭据或已有 SSH 密钥。仓库不携带账号授权和本机桥接密钥。

## 1. 在部署电脑上启动

```bash
git clone https://github.com/zyileven/workbuddy-subscription-bridge.git ~/workbuddy-subscription-bridge
cd ~/workbuddy-subscription-bridge
docker compose up -d --build --wait
curl --fail http://127.0.0.1:8787/health
```

若已经安装并登录 GitHub CLI，可以用
`gh repo clone zyileven/workbuddy-subscription-bridge ~/workbuddy-subscription-bridge`
完成同一次克隆。

健康检查只证明服务存活，首次部署还需要浏览器授权。Compose 只将 8787
和 1455 发布到部署电脑的 `127.0.0.1`；外部设备通过下面的 SSH 隧道访问。

## 2. 浏览器授权

**如果能在部署电脑直接使用浏览器**，在该电脑执行：

```bash
cd ~/workbuddy-subscription-bridge
docker compose exec bridge node src/cli.mjs login --host 0.0.0.0 --no-open
```

保持命令运行，在该电脑浏览器中打开打印的链接，完成 ChatGPT 账号登录与套餐授权。

**如果部署电脑是无桌面的远程主机**，先在有浏览器的电脑上打开终端 A，
把 `USER@REMOTE_HOST` 替换为远程主机的 SSH 登录地址：

```bash
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -L 127.0.0.1:1455:127.0.0.1:1455 \
  -L 127.0.0.1:8787:127.0.0.1:8787 \
  USER@REMOTE_HOST
```

保持终端 A 运行。在终端 B 登录远程主机：

```bash
ssh USER@REMOTE_HOST
cd ~/workbuddy-subscription-bridge
docker compose exec bridge node src/cli.mjs login --host 0.0.0.0 --no-open
```

复制终端 B 打印的链接，到本地浏览器打开。回调仍是
`http://127.0.0.1:1455/auth/callback`，会通过终端 A 的隧道到达远程容器。
不要修改授权链接中的回调地址。登录命令成功后可关闭本地浏览器页面。

在部署电脑确认：

```bash
docker compose exec bridge node src/cli.mjs status
docker compose exec bridge node src/cli.mjs models
docker compose exec bridge node src/cli.mjs key
```

需要 `connected: true`、`plan_usage_enabled: true`。最后一条输出的是这次部署
新生成的桥接密钥：WorkBuddy 必须改填这个值，不能继续使用旧电脑的桥接密钥。
账号密码、access token 和 refresh token 不填写到 WorkBuddy 中。

## 3. 连接 WorkBuddy

如果 WorkBuddy 与容器部署在同一台电脑上，可以直接访问
`http://127.0.0.1:8787/v1/chat/completions`。

如果 WorkBuddy 仍在自己的笔记本上运行，日常使用期间保持 8787 的 SSH
转发在线。首次登录时的终端 A 已包含这个转发；后续也可以只保留服务端口：

```bash
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -L 127.0.0.1:8787:127.0.0.1:8787 \
  USER@REMOTE_HOST
```

连接中断后需要重新执行该命令。SSH 隧道不在线时，本地地址不可用；容器继续
在远程主机运行。需要开机自动建立隧道时，可按客户端操作系统将此命令放入
登录启动项或用户服务，使用已有的 SSH 密钥登录。

在 WorkBuddy 自定义模型中填写：

| 项目 | 配置 |
| --- | --- |
| 完整接口地址 | `http://127.0.0.1:8787/v1/chat/completions` |
| 模型 ID | `gpt-6.1-sol-bridge`，上游为 `gpt-6.1-sol` |
| API Key | 部署电脑上 `key` 命令的输出 |
| 协议 | Chat Completions；自定义协议开启 |
| 工具调用 | 开启 |

这个独立模型 ID 用来与已有的直连模型区分；实际账号必须能在 `models`
输出中看到 `gpt-6.1-sol`。其他模型可使用目录中返回的真实 slug。

手动编辑 `~/.workbuddy/models.json` 时，参考
[单个模型条目示例](../examples/workbuddy-model.json)，只添加或更新桥接条目，
保留其他模型。示例的 `apiKey` 故意留空。

修改配置后，在 WorkBuddy 里重新选择此模型。如果已有对话报
`has no endpoint url configured`，而配置中已经有 URL，先完全退出并重新打开
WorkBuddy，让其后台进程加载最新配置，再重试。

先验证一句普通问答，再在专用测试目录验证只读工具任务，并到 ChatGPT 用量页
核对使用记录。下面的命令也能在部署电脑发出一次小型真实请求，会产生用量：

```bash
docker compose exec bridge node src/cli.mjs verify --model gpt-6.1-sol
```

## 4. 持续运行与更新

容器设置了 `restart: unless-stopped`，账号数据保存在命名卷
`workbuddy-subscription-bridge_bridge-data`。容器重建和镜像更新会继续使用这个卷。
运行期间，服务会在令牌到期前刷新，刷新成功后将旋转后的令牌保存回数据卷。

部署电脑必须保持开机、不休眠，并让 Docker 引擎随系统启动。
在使用 systemd 的 Linux 主机上，可执行：

```bash
sudo systemctl enable --now docker
```

macOS 上开启所用 Docker 管理应用的登录启动，并按电脑用途设置休眠。
手动 `stop` 或 `down` 后，先执行 `docker compose up -d --wait` 恢复服务。
容器重启不会替代失效或被撤销的账号授权；遇到明确的登录失效错误，需要重新登录。

日常检查和更新（在部署电脑执行）：

```bash
cd ~/workbuddy-subscription-bridge
docker compose ps
docker compose logs --tail=50 bridge
git pull --ff-only
docker compose up -d --build --wait
```

正常停止并保留账号数据：

```bash
docker compose down
```

`docker compose down -v` 会删除账号数据和桥接密钥。GitHub 只保存源码；
不要将 OAuth 凭据、命名卷内容或填过 Key 的 WorkBuddy 配置提交到仓库。
